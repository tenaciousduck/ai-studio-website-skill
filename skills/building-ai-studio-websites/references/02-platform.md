## Who owns what

| Thing | Owner | Notes |
|---|---|---|
| Site code (`src/routes`, `src/components`, `src/lib`) | Claude | Reaches `main` by pull request, following the setup file |
| `src/integrations/payments/*` | AI Studio | Sealed, regenerated on enable. Use it, never edit it |
| `src/integrations/supabase/*` | AI Studio | Generated. `types.ts` is regenerated by migrations |
| `src/lib/tracking.ts` | AI Studio | Leave it alone; copy its ids for server-side sending |
| `src/routeTree.gen.ts` | Generated | Never hand-edit |
| Schema changes | AI Studio's Cloud migration tool | Strict prompt in `prompts.md` |
| Custom field registration | AI Studio or CRM settings | Ids go in one file in the repo |
| Publishing, Payments mode | The builder | Claude never publishes |
| CRM contacts, tags, workflows | CRM | Document every workflow in the repo |

## The stack

The first project used TanStack Start, React 19, Tailwind 4, shadcn/Radix, Supabase and Nitro building for Cloudflare, through `@leadconnector/vite-tanstack-config`. That package already includes the framework plugins, so adding them again breaks the app. `vite.config.ts` says so at the top. Bun's lockfile; tests with `npx bun test`.

**Confirm a new project matches before using this chapter or the templates:** check `.vibe/project.json` (`template: tanstack_start_ts`), the versions in `package.json`, `AGENTS.md`, and whether `src/integrations/` holds the same folders. Note any differences in the project's `CLAUDE.md`, then update this chapter.

## Sync, publishing and "Diverged"

- Commits on the connected branch sync into AI Studio. Keep that branch working at every push.
- **Merging doesn't publish.** Nothing reaches visitors until the builder publishes.
- **Admin edits and uploads skip all of this.** They hit the live database immediately.
- AI Studio only pulls when it has no versions of its own waiting. A Restore, an AI Studio edit or an automatic save can leave one behind, which blocks the pull with "Diverged". It happened twice in two days from no-op saves: a generated file blanked then restored, and `.env` lines reordered.

**When "Diverged" appears:**

1. Tell the builder to click **New branch**, never **Force push**. Force push makes AI Studio's copy win and wipes `main`. Warn them of this before any merge.
2. Ask for the branch name. Read what those versions changed. Compare `.env` values by hash; never print them.
3. Merge `origin/main` into that branch. Run tests and the build.
4. Following the setup file, push the same commit to both that branch and `main`, as plain forward pushes. A push right after a merge can fail once; wait a few seconds and retry.
5. Have the builder re-check, confirm it shows synced, then publish.

Once one such branch exists, keep it on the same commit as `main` after every merge, so it doesn't matter which one AI Studio is connected to.

After any merge, don't say it reached AI Studio until the builder confirms it or the preview shows it.

## Database and sign-in

- The app's database lives in AI Studio's account, not the builder's own Supabase account. A Supabase connector can't reach it, and a similarly named project in that account may be unrelated. Never touch it by assumption.
- Files in `supabase/migrations/` are a record of what ran, not triggers. AI Studio's tool applies the SQL and writes its own file. Delete your draft copies before merging, or history will hold two records.
- Data-only changes (`run_sql`) aren't recorded as migrations.
- **Keep migrations additive.** Old code must keep working while a phase is in progress. Prefer one `jsonb` wording column to dozens of text columns. Avoid Postgres reserved words as column names.
- Apply migrations before merging code that writes the new columns, or saves fail.
- No service-role key exists locally, by design. Editor checks should use the caller's own session, through the `has_role` database function, so `/admin` works locally. Claiming the first editor only works on the hosted site.
- Fail closed: a new row's visibility defaults to draft, and a failed admin count must never read as "zero admins".
- AI Studio's security advisor repeats a known finding on `public.has_role`. Read it, but don't assume every repeat is new.
- `src/start.ts` comes from the boilerplate and already has the cross-site protection (`createCsrfMiddleware`). Change only the `functionMiddleware` line; never rewrite the file.
- `.env` is generated and tracked in git, and AI Studio may rewrite it. It holds public values only. Never put secrets there.

## Hosting behaviour

Check these on each new host with `curl -I`:

| Path | First project |
|---|---|
| Built `/assets/*` | `max-age=31536000, immutable`. Fonts and image copies belong here |
| `public/*` | `max-age=0, must-revalidate`. Not a home for heavy files, whatever a brief says |
| HTML | `no-cache`, served through Cloudflare. No page caching |
| `www` | 301 to the bare domain, so the bare domain is official |
| AVIF | Sent with no `Content-Type`. Browsers still show them |

Every published page also loads AI Studio's visit statistics (`/__vibe/analytics.js`), which sets a 30-minute cookie for every visitor and records IP addresses. Cloudflare adds `__cf_bm`. The site's code couldn't turn either off, so the privacy page must say so (`09-legal.md`).

Preview: a signed-in person can check a version in AI Studio's Preview before publishing. The address `https://preview-<project id>.vibepreview.app` answered on the first project, but automated tools couldn't read it, so automated checks ran on the live site.

## Build failures

A failed AI Studio build isn't necessarily your code. Run the production build locally first.

- `assets-upload-session … status 500, code 10013` at the hosting step, then `GCS upload returned HTTP 412` on every retry: retrying the same version can't work. Merge a small docs change to make a **new** version, and that got a real try.
- If a fresh version fails the same way, it's for HighLevel support.

## Trusting AI Studio's answers

AI Studio reads code and is often right about sealed contracts. It's weaker on CRM behaviour, and it doesn't know what's been tested. On the first project it:

- said the quantity box couldn't be hidden from the page, when one CSS rule hid it;
- blamed product setup when the checkout simply had no shipping step;
- claimed the site shipped US-only and raised risks already handled by workflows;
- recommended fonts in `public/` for long caching, which the live headers disproved;
- wrote a form event with a space in its type, which the CRM accepts and silently drops;
- made an image change that altered no bytes and reserved the wrong space.

It also found real bugs: its form audit caught two forms that ignored failures. So use it as a second reviewer, and verify in both directions. Its assistant will also make small undisclosed edits if a prompt allows it, which is why prompts forbid them.

If other people or tools also work on the CRM or site, keep a handover list of who owns what.
