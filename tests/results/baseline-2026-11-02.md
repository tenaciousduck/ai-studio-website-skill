# Baseline results, 2026-11-02

Scenarios run with the plugin as it stood before the audit skill existed (build skill only), against `tests/fixtures/sample-site`. Each run was a fresh general-purpose subagent, told not to read the fixture's `README.md` (the answer key) and to edit nothing outside a scratch copy. Full outputs are kept outside the repo. Quotes are word for word.

Criteria come from `tests/skill-scenarios.md`. "Planted problems" are the nine numbered items in the fixture README.

## Summary

| Scenario | Criteria passed | Planted problems found | Main failure |
|---|---|---|---|
| S1 | 3 of 7 | 9 of 9 | No opener, no fixed report shape, Selling and checkout and Admin not marked Not applicable |
| S2 | 2 of 4 | 2 of 2 asked about (plus 4 others as asides) | Went straight into repair work; no single-area audit, no repair-session offer |
| S5 | 1 of 3 | 9 of 9 | Fixed files during the "audit", and never explained why it shouldn't |

Finding the problems was never the gap. All three runs found all nine, because the build skill's chapters describe the same traps. What failed is process: read-only discipline, the shape of the output, and scope.

## Across all three runs

- Test contamination: all three runs read the builder settings file (`~/.claude/ai-studio-setup.md`), which the skill is meant to read. On this test machine that file holds one builder's own preferences, so the baselines partly reflect those settings and not the skill alone.
- All three leaned on "past experience" with the platform, and only some of that was labelled as an estimate. None marked each result as measured, estimated or unverified the same way.
- Nobody was told what an audit would not do. Each run started from "what is wrong" and moved to "how I'd fix it" within the same message.

## What the audit skill must fix

1. Show a short opener (under 150 words) before any findings: what an audit is, that it changes nothing, what is about to be checked.
2. Give a fixed report shape, grouped by area, with every area present. Mark areas that don't apply as Not applicable (Selling and checkout, Admin), never as a finding or a question.
3. Use a named "What we couldn't check" section for everything that needs a live site or a permission that was refused.
4. End with one next-session line, not a plan and not a list of questions.
5. Keep audit and repair apart. Audit sessions edit nothing, not even a scratch copy. When an owner says "fix as you go", say no, say why in one plain sentence (the report stays trustworthy, and nothing is changed before the owner has seen the whole picture), and carry on read-only.
6. When the owner names one area (such as the contact form), audit only that area, then offer one repair session, then offer the full audit at the end. Mention other findings in one line at most, and don't go wider.
7. Ask permission before any live test of a form or payment, name its real-world effects, and don't run it without a yes. This part already worked; keep it.
8. Label every result as measured, estimated or unverified. A lesson from another site is "unverified for this site", never a statement about this site's CRM or platform.
9. Never state legal conclusions as fact. Say "best practice" or "judgment call", and keep the not-legal-advice line next to any legal item.
10. Don't assume a country. If it matters, ask once, and say which checks wait on the answer.
11. Keep owner-facing words plain: explain "CRM", "robots.txt" and similar terms on first use; don't expose internal ids, tag names or workflow settings unless the owner asked.
12. Ask few questions, and only those that block the next step. No nine-question lists.
13. Don't pad the report with absences that come from seeing only part of a repo (no tests, no lock file, no notes file).
14. Say when a size or speed can't be measured from the code (the hero image stand-in), instead of calling it simply a placeholder.
15. Scenario runs must tell agents to treat the builder settings file as absent, so results reflect the skill alone.
16. Keep one rule from the baseline: leave platform-generated files such as the tracking helper alone, and put any fix beside them in a later repair session.
